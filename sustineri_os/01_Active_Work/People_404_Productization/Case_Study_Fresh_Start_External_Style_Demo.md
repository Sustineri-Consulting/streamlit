# External-Style Demo Case — Fresh Start Counseling

**Status:** Demo-style *framework* only. **A proposed audit lens, not completed findings.**

> **Important:** This file does **not** invent facts and does **not** claim any audit was
> performed. It shows *how* People 404 would review an organization like Fresh Start
> Counseling. Any statement below is framed as "what we would examine," not "what we found."
> Do not publish this as a completed case study.

**Purpose:** Demonstrate the People 404 method on a familiar, external-style example, and
show how a *website review* converts into an *operational infrastructure review*.

---

## The move People 404 makes

Most reviews of a counseling practice stop at the website: does it look good, is it clear,
does it convert? People 404 uses the website as a doorway into the **operational
infrastructure** behind it — the roles, dependencies, and undocumented work that make the
visible experience possible (or fragile).

**Website review → operational review, by asking:** for each thing a visitor sees, *who and
what has to work behind it, and what breaks if that person or tool is unavailable?*

## Review perspectives (the audit lens)

Each perspective is a set of questions we *would* ask — not conclusions.

**1. Patient seeking care**
- Can I quickly tell what's offered, whether I qualify, and how to start?
- What happens after I reach out — and who handles that, behind the scenes?

**2. Future patient**
- Is availability and fit clear enough to decide?
- What operational step (intake, scheduling, screening) does my journey depend on?

**3. Site navigator (usability)**
- Can any visitor find the key path without confusion?
- Where would a broken link or unclear step create a support burden for staff?

**4. Future provider interested in packages**
- Is it clear how a provider would join or use a package?
- What onboarding/credentialing work sits behind that, and who owns it?

**5. Founder / owner**
- Which parts of the visible experience depend on the founder personally?
- What would stall if the founder were unavailable for two weeks?

**6. Compliance / advertising risk**
- Do claims, testimonials, and language stay within professional/advertising guidelines?
- Who reviews content before it goes live, and is that a documented step?
- _(Flag for professional/legal review — not a legal opinion.)_

**7. Professional solopreneur / founder interested in a secure location**
- Is sensitive intake handled securely and privately?
- What tools/vendors carry that responsibility, and is there a backup?

**8. Package review lens**
- Are packages clearly defined, priced, and deliverable with current capacity?
- Does any package quietly depend on one person to fulfill?

**9. UI / UX lens**
- Where does friction in the interface create hidden manual work for staff?

**10. Operational dependency lens**
- Behind the site: scheduling, intake, billing, records, communications — which are single
  points of failure? Which are undocumented? Which one person holds together?

## How the conversion works in practice

1. Start with the public experience (the website).
2. For each visible promise, trace the operational chain that fulfills it.
3. Map that chain onto the connective map (role → depends on → depended on by → risk).
4. Surface the single points of failure and undocumented work behind the friendly front end.
5. Deliver a repair plan for the *operation*, not just the *website*.
